# 算子作业可视化基础对象与原语封装规划

> 文档版本：v1.0
> 更新时间：2026-09-09
> 适用范围：PyPTO / PTO 算子开发、编译、调试、精度验证、性能调优与模型集成工具链
> 目的：把 `Design/` 下各原型中反复出现的可视化，抽象成一组**可封装、可被智能体调用**的基础作业对象

---

## 1. 为什么要做这层抽象

`Design/` 目前有 20 余个原型（Toolkit Studio、Memory Inspector、Pass Decision Studio、编译失败诊断、性能调优 Lab、Artifact Hub、Model Inference Studio 等）。逐个读下来会发现：

- **场景在变，图不变。** 计算图出现在 Coding、调试、模型集成三个场景；泳道出现在 Runtime 调试和性能调优；Diff 出现在 IR、源码、契约、基线四处。
- **实现各写各的。** `run-timeline.js` 的 `taskTrack/laneTrack`、`qwen3-performance-swimlane.js`、`inference-profiler.js` 里的时间轴，三份代码画的是同一个东西。
- **智能体真正要产出的不是图，是对象。** Agent 应该产出「这是一张依赖图，节点是 Task，异常边是这两条，锚点回到源码第 118 行」，而不是产出一段 HTML。

所以抽象要分成两层，混在一起是目前原型难以复用的根因：

| 层 | 是什么 | 谁负责 |
|---|---|---|
| **作业对象层（Domain Objects）** | 算子域的名词：Operator、Tensor、Tile、Pass、Task、MemBlock、Run、Finding… | 智能体产出 |
| **可视化原语层（View Primitives）** | 渲染这些名词的通用图元：Graph、Timeline、Diff、Heatmap… | 前端封装 |

**封装的边界：智能体只输出「作业对象 + 用哪个原语呈现」的结构化 payload，绝不输出 HTML/SVG。**

## 2. 第一层：作业对象（Domain Objects）

这是所有可视化的数据地基，也是跨视图联动的唯一凭据。共 11 类，每类都必须有全局唯一 `id`，且可回链到源码 `span`。

| 对象 | 关键字段 | 产生阶段 | 已有承载 |
|---|---|---|---|
| `Operator` | name、契约（In/Out/InOut）、backend、变体、调用点 | 源码解析 | `operator-inspector.js`、`operator-scan.js` |
| `OpNode` | 计算语义（Matmul/RMSNorm/RoPE/Softmax/Reduce/Cast）、scope、span | 源码解析 / IR | `passes-graph.js`、各 `render*ComputationGraph` |
| `Tensor` | shape、dtype、layout、stride、memory space、方向、生产者/消费者 | 源码 / IR / Runtime | `kf-pa-tensor-table` |
| `Tile / Chunk` | 父 Tensor、切分维度、真实区域、Padding、尾块、M/N/K 映射 | 源码 / IR | `kf-pa2-tile-steps` |
| `Pass` | 顺序、耗时、required/produced/invalidated、IR 规模、诊断 | 编译 | `ir-pipeline-data.js`、`ir-compile-guard.js` |
| `Scope` | 类型（Orchestration/Group/InCore/AIC/AIV/Inline）、嵌套、并行域 | 源码 / IR | `kf-pto3-loop-tree` |
| `Task` | kernel、core、ring、起止时间、依赖边、等待原因 | Runtime | `run-trace-data.js`、`run-timeline.js` |
| `MemBlock` | space（Vec/Mat/Acc/Left/Right）、地址区间、生命周期、复用关系 | 编译 / Runtime | `ir-pass-visuals.js` 的 `packing()`、`run-fan.js` |
| `Metric` | 名称、值、单位、基线、门禁阈值、采集窗口 | 静态估算 / 实测 | `kf-rd-kpi`、`inference-profiler.js` |
| `Run` | runId、输入、环境、产物、状态、关联基线 | 执行 | `task-history.js`、`operator-artifact-hub` |
| `Finding` | 结论句、触发条件、证据集、影响面、建议动作 | Agent | `kf-conclusion`、`operator-inspector.js` 的 risk/guard |

### 2.1 三个横切契约（所有对象共有）

这三项是「可被智能体调用」的关键，缺一项这套封装就退化成普通图表库。

**① Anchor（锚点）** — 双向联动的唯一机制
```
anchor: { file, span:[startLine, endLine], objectId, runId }
```
任何图元的任何元素点击后，只做一件事：往联动总线广播 `anchor`。源码区、IR 区、Trace 区各自订阅并高亮。这样 N 个视图的联动复杂度从 N² 降到 N。

**② Provenance（可信度）** — 已在 `operator-inspector.js` 中落地为 5 档，直接沿用
```
origin: 'fact' | 'resolved' | 'compiled' | 'estimated' | 'measured'
       (源码事实)  (跨文件解析)  (编译事实)   (静态估算)    (运行实测)
```
**强制字段。** 智能体不允许把静态估算画成和实测一样的样式。图元统一负责渲染角标与图例，智能体只负责填对。

**③ Action（动作）** — 图上每个结论都可执行
```
actions: [{ kind:'locate'|'explain'|'gen_test'|'dump'|'recompile'|'compare'|'apply', payload, needsConfirm }]
```
高开销采集和改代码类动作 `needsConfirm: true`。

## 3. 第二层：可视化原语（14 个图元 + 2 个载体）

### 3.0 两个载体（不是图，是所有图元的挂载面）

| # | 原语 | 职责 | 已有实现 |
|---|---|---|---|
| L1 | **SourceCanvas** 源码锚面 | 行高亮、区段条、随滚动的 sticky 段落指示、行内标注（风险/dump 点） | Toolkit Studio 源码区、`kf-source-region` |
| L2 | **FindingCard** 结论证据卡 | 结论句 + 触发条件 +（折叠的）证据 + 动作按钮 + provenance 角标 | `kf-conclusion`、`kf-evidence-node` |

`FindingCard` 是复用度最高的对象——每个场景的右侧面板第 2 层「关键结论」都是它。建议**第一个封装**。

---

### A 组 · 结构类（回答「是什么结构」）

#### A1 GraphView — 有向图
- **回答**：数据怎么流？谁依赖谁？链路在哪断了？
- **复用场景**：算子计算图、Task 依赖图、Pass 依赖图、模型层图、融合覆盖图、证据链图
- **契约**：`{ nodes:[{id, label, kind, badges, anchor, origin}], edges:[{from,to,kind,label}], layers?, layout:'dagre'|'layered' }`
- **必备变体**：
  - **图层开关**（已在 `5c8df71b` 提交中落地为可叠加图层：精度层、风险层、覆盖层）——这是把 6 张图合并成 1 张的关键
  - **断链/无生产者**高亮
  - 节点点击 → 广播 anchor（`d9897429` 修的就是这个）
- **已有实现**：`passes-graph.js`、`renderQwenDecodeComputationGraph`、`renderPagedAttentionComputationGraph`、`decode-layer-graph/`

#### A2 TreeView — 层级树
- **回答**：Scope 怎么嵌套？循环怎么嵌套？哪层是并行域？
- **复用场景**：Scope/Inline 层级、循环树、文件与产物树、Pass 分组
- **契约**：`{ roots:[{id,label,kind,parallel?,metrics?,children,anchor}], columns? }`
- **变体**：带右侧指标列（树形表格）、并行域着色
- **已有实现**：`kf-tree-row`、`kf-pto3-loop-tree`

#### A3 TopologyView — 硬件拓扑 + 数据流叠加
- **回答**：这段代码在硬件上走了哪条路？GM→L1→L0A→Cube→L0C 还是 GM→UB→Vector→UB→GM？
- **与 GraphView 的区别**：**版式是人工设计的固定底图**（Cluster / Cube / Vector / 存储层级），智能体只提供「点亮哪些节点、流过哪些边、方向和速率」的叠加层。不能用自动布局。
- **契约**：`{ platform:'A2'|'A3'|'A5', highlight:[nodeId], flows:[{path:[nodeId], bytes, dir, phase}], annotations:[{nodeId, metric, origin}] }`
- **变体**：静态映射 vs 实测路径（必须视觉区分）、分步动画（融合前后对比）
- **已有实现**：`fusion-hardware-view.js`（含分步动画与 preset）、`renderMatmulHardwareGraph`、`renderRmsNormHardwareGraph`、`pass-atlas/hw.js`

#### A4 TilingView — 分块映射
- **回答**：`8192 = 16 × 512` 是怎么切的？尾块在哪？Padding 消费了吗？
- **契约**：`{ tensor:{dims,dtype}, splits:[{dim, chunks, tileSize, remainder}], loopVars:[{name,dim}], mnk?:{m,n,k}, padding:[range] }`
- **变体**：一维切分条、二维网格、M/N/K 三视图、尾块与不可整除告警
- **已有实现**：`kf-pa2-tile-steps`、`renderPto3TileLabInspector`

### B 组 · 时间类（回答「什么时候、多久」）

#### B1 TimelineView — 并发泳道
- **回答**：Cube 和 Vector 重叠了吗？谁在等？流水空洞在哪？
- **复用场景**：Runtime Swimlane、Cube/Vector/DMA 泳道、Token/Layer/Kernel 三层时间线、L2 Swimlane
- **契约**：`{ span, lanes:[{id,label,kind}], blocks:[{lane,start,end,taskId,state:'run'|'wait'|'idle',label,anchor}], marks:[{t,label}], criticalPath:[taskId] }`
- **变体**：泳道维度切换（by Core / by Ring / by Kernel）、等待原因着色（slot wait / fence wait / backpressure）、关键路径描边、区间缩放刷选
- **已有实现**：`run-timeline.js`（`taskTrack`+`laneTrack`+`axis`）、`qwen3-performance-swimlane.js`、`inference-timeline.js`

#### B2 SequenceView — 顺序阶段轴
- **回答**：Pass 按什么顺序跑的？哪个 Pass 真正改了结构？哪一步失败？
- **与 B1 的区别**：无并发、强顺序、每步带前后状态与增量指标；支持「无变化步骤折叠聚合」
- **契约**：`{ steps:[{id,label,status,durMs,deltaMetrics,diagnostics,changed:bool,anchor}], collapseUnchanged:true, firstFailure?:stepId }`
- **变体**：Pass 时间线、编译阶段轴（parse→passes→codegen）、逐 Pass 数值二分（每步带 pass/fail 徽标）、Run 步骤条
- **已有实现**：`ir-pipeline-data.js` + `ir-compile-guard.js`、`renderPasses`、`kf-steps`

#### B3 BreakdownView — 分解 / 瀑布
- **回答**：这段总耗时（或总内存、总流量）由什么构成？谁贡献最大？
- **与 B1 的区别**：**表达构成，不表达并发**。总量 = 各分项之和。
- **契约**：`{ total:{value,unit}, parts:[{label,value,kind,children?,anchor,origin}], mode:'waterfall'|'stacked'|'sunburst' }`
- **变体**：耗时瀑布（计算/搬运/同步/调度/空闲）、SLO 分解（排队/Prefill/Decode/采样/返回）、编译耗时火焰图、带宽流量构成、可逐级下钻
- **已有实现**：`inference-profiler.js`、`kf-rd-summary`

### C 组 · 数值类（回答「多少、分布在哪、够不够」）

#### C1 MetricView — 指标卡 / 仪表 / 门禁
- **回答**：当前值多少？相对基线如何？过没过门禁？
- **契约**：`{ items:[{label, value, unit, baseline?, delta?, threshold?, state:'pass'|'warn'|'block', origin, anchor}], layout:'kpi'|'gauge'|'bar' }`
- **变体**：KPI 行、利用率仪表、门禁徽标、评分条
- **已有实现**：`kf-rd-kpi`、`kf-rmsl-gauge`、`kf-gate`、`renderScoreBar`

#### C2 DistributionView — 分布
- **回答**：误差是集中还是弥散？容差定得合理吗？
- **契约**：`{ bins:[{lo,hi,count}], stats:{max,mean,p99,nan,inf}, refLines:[{value,label}], scale:'linear'|'log' }`
- **变体**：绝对/相对误差直方图、ULP 分布、耗时分布
- **已有实现**：`renderHistogram`

#### C3 HeatmapView — 二维热图
- **回答**：错值是局部还是系统性？落在 Padding 区吗？参数扫描的甜点在哪？
- **契约**：`{ rows, cols, values, colorScale:'diverging'|'sequential', masks:[{region,label}], topK:[{r,c,value}] }`
- **变体**：Tensor 误差空间热图（含 Padding 区遮罩、Top-K 异常定位）、参数二维扫描热图（含合法区/越界区/数值失败区分区）
- **已有实现**：`inference-profiler.js`、`task-history.js`（部分）

#### C4 ScatterView — 散点 / 前沿 / 敏感性
- **回答**：受限于算力还是带宽？哪些候选在 Pareto 前沿上？调这个参数收益曲线怎么走？
- **契约**：`{ points:[{x,y,label,state,anchor}], axes:{x,y}, envelopes?:[{label,path}], frontier?:[pointId], refCurves?:[] }`
- **变体**：Roofline（含屋顶线包络）、Pareto 前沿、单参数敏感性曲线、多 Run 对比散点
- **已有实现**：`inference-profiler.js` 的 `renderRoofline`、`kf-prof-roofline`

#### C5 OccupancyView — 空间占用（地址 × 时间）
- **回答**：UB/L1/L0 装得下吗？谁和谁重叠了？Ring Slot 什么时候释放？
- **这是本工具链最特殊、最不可替代的一个图元**，通用图表库没有对应物。
- **契约**：`{ space:'Vec'|'Mat'|'Acc'|..., capacity, blocks:[{id,label,offset,size,birth,death,reuseOf?,conflict?,anchor}] }`
- **变体**：地址打包图（矩形 = 地址区间 × 生命周期）、容量包络曲线随时间、Ring Buffer Slot 占用、重叠冲突高亮
- **已有实现**：`ir-pass-visuals.js` 的 `packing()`、`run-fan.js` 的 `envelope()`、`memory-inspector/Memory_V2.html`、`pass-atlas/pack.js`

---

### D 组 · 对照与凭据类（回答「变了什么、可不可信」）

#### D1 DiffView — 对照
- **回答**：这一步改变了什么？和基线比差在哪？
- **契约**：`{ mode:'side-by-side'|'inline'|'structural', left:{label,ref}, right:{label,ref}, changes:[{kind:'add'|'del'|'move'|'modify', path, before, after, anchor, impact}] }`
- **变体**：
  - 源码 Diff / IR 结构化 Diff（op 增删移改 + shape/dtype/layout/attrs 变化）——已按业界左右对照定稿（`7790362c`）
  - 契约 Diff（修改前后的 In/Out/shape/dtype）
  - 基线因果 Diff（参数变化 → 指标变化，两栏并列 + 归因列）
  - 图 Diff（GraphView 的叠加着色模式，非独立实现）
- **已有实现**：`renderCodeDiff`、`ir-compile-guard.js`、`renderRunComparison`、`kf-prof-cmp`

#### D2 MatrixView — 状态矩阵
- **回答**：哪一层开始不一致？哪些边界还没覆盖？这个 API 在哪些平台可用？
- **契约**：`{ rows:[{id,label}], cols:[{id,label}], cells:[{r,c,state:'pass'|'fail'|'na'|'missing', detail, anchor, origin}] }`
- **变体**：Oracle 矩阵（Torch / 原始 Program / Pass 后 IR / Device）、边界用例覆盖矩阵、API×平台支持矩阵、融合规则覆盖矩阵
- **已有实现**：`renderOracles`、`renderCoverage`、`fusion-catalog-*`、`kf-fus-cov`

## 5. 智能体调用接口设计

### 5.1 统一调用形态

智能体不调用 14 个不同的 API，只调用一个：

```jsonc
// Agent 输出的一个「可视化作业单元」
{
  "id": "vb-ub-conflict-01",
  "primitive": "OccupancyView",
  "title": "UB 地址区间与 Ring Buffer 预留区重叠",
  "origin": "compiled",              // 强制
  "anchor": { "file": "decode_layer.py", "span": [412, 438] },
  "data": { /* 该原语的契约 */ },
  "finding": {                        // 可选，挂在图上的结论
    "verdict": "当前 Tile 工作集 152KB 超出 UB 可用区 128KB",
    "trigger": "AllocateMemoryAddr 之后",
    "evidence": ["pass:AllocateMemoryAddr", "memblock:ub_tile_2"],
    "actions": [
      { "kind": "locate", "payload": { "anchor": "..." } },
      { "kind": "apply", "payload": { "tileM": 64 }, "needsConfirm": true }
    ]
  }
}
```

前端只需要一个 registry：`render(container, block)` → 按 `primitive` 分发。新增图元不改调用方。

### 5.2 三条硬约束

1. **智能体不产出 HTML/SVG**，只产出上面这种 payload。目前原型里大量 `renderXxx` 直接拼 HTML 字符串，是复用的最大障碍。
2. **`origin` 不可缺省**。缺省则图元按 `estimated` 降级渲染并显示警示，杜绝把推断包装成实测。
3. **所有交互只广播 anchor**，不直接操作其他视图。联动由总线统一调度。

### 5.3 分层封装建议

```
@pto-viz/core        // anchor 总线、provenance 渲染、action 分发、主题令牌
@pto-viz/primitives  // 14 个图元，纯函数：(container, data) => dispose()
@pto-viz/blocks      // FindingCard / SourceCanvas 两个载体
@pto-viz/schema      // JSON Schema + TS 类型，前后端和 Agent 共用同一份
```

`@pto-viz/schema` 应作为**智能体的工具定义（tool schema）直接下发**——这样 Agent 的输出天然合法，不需要后处理校验。

## 6. 落地优先级

| 批次 | 内容 | 依据 |
|---|---|---|
| **P0** | `core`（anchor 总线 + provenance）、`FindingCard`、`SourceCanvas`、`GraphView`、`MetricView` | 全场景覆盖，且是其他图元的挂载前提 |
| **P1** | `DiffView`、`SequenceView`、`MatrixView`、`OccupancyView` | 支撑「可信编译」与「精度」两条 P0/P1 业务线 |
| **P2** | `TimelineView`、`BreakdownView`、`TopologyView`、`TilingView` | 支撑性能调优与硬件心智模型 |
| **P3** | `HeatmapView`、`ScatterView`、`DistributionView`、`TreeView` | 深度分析，出现频次相对低 |

## 7. 明确不抽象的部分

以下内容**不应**进原语库，硬塞进来会让契约膨胀而复用率反降：

- **一次性叙事插画**：如 IR Pass 快照里的定制示意图、白皮书里的架构图。这类图的价值在于人工编排的版式，抽象后反而失效。
- **页面框架与布局**：左侧资源管理器 / 中间工作区 / 右侧面板 / 底部证据区，属于工作台外壳，不是图元。
- **领域数据加工逻辑**：如何从 Trace 算出关键路径、如何做 IR 结构化 Diff——属于智能体或后端能力，图元只负责画已经算好的结果。
- **模型/算子特有的定制视图**：`renderPagedAttentionInspector` 这类，应拆成「通用图元 + 该算子的数据装配」，装配部分留在业务侧。

---

## 8. 与现有原型的迁移路径

不建议一次性重写。建议：

1. **先抽 schema，不动实现。** 给现有 `renderXxx` 补一层输入契约，确认 14 个图元的字段能覆盖所有现存调用。
2. **先统一 anchor 总线。** 当前联动是点对点的（`d9897429` 这类 bug 的来源），换成广播后即可先收敛一批问题。
3. **按 P0 顺序替换。** 每替换一个图元，同步下线对应的重复实现（如 `run-timeline.js` / `qwen3-performance-swimlane.js` / `inference-timeline.js` 三份泳道合一）。
4. **以 Toolkit Studio 作为首个宿主**，验证通过后再回迁其余原型。
